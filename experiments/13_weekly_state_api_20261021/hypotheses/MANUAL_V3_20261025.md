# Manual website study v3: Python-guided weekly choices

**Prepared 25 October 2026 after the user reaffirmed a $5 maximum and requested website prompts. No website results have been received for this version.** It is separate from the closed weekly API sample and the uncollected v2 API proposal. No repository API calls are required.

1. **One chat produces a batch:** ten four-role chains, 40 fictional students, 24 scored weeks. The website's Python tool maintains state; the model chooses 40 literal orders after each displayed week. Python must never generate an ordering policy or choose orders.
2. **One independent matched block contains three fresh chats:** A adequate review/control, B first response/control, C first response/causal education. A records an initial proposal and receives a separate model/tool interaction to reconsider before commitment. B/C commit their first proposal. Chats do not see the other arms' choices.
3. **The statistical sample is independently started blocks.** Ten chains in one chat are dependent and averaged before analysis. Larger batches improve within-chat averaging, not the independent sample size. Shared demand/profile seeds match arms/models; generated decisions are never shared across them.
4. **This tests a reconsideration-opportunity analogue.** It does not impose calibrated clock time or demonstrate subjective time pressure. Pipeline sensitivity is an assay proxy, not identified underweighting. The original literal human H1–H4 remain unverified by an AI-only opportunity analogue.

## Required website behavior

The website must have Python/code execution. Upload the supplied standalone controller and paste the assigned prompt. The model initializes the named case, prints only `display()`, chooses literal decisions, and submits them to the controller. Each decision follows a returned tool display. A's initial and reconsideration proposals must occur in **separate model/tool interactions**. A single code cell containing an automatic ordering algorithm, a precomputed full trajectory, or both proposals does not satisfy this protocol.

Controller calculations cover demand, arrivals, shipments, inventory, backlog, costs, histories and state hashes. Future demand is not printed. However, the model can inspect the uploaded source/internal state; this is procedural concealment, not enforced access isolation. The prompt forbids reading future demand or internal random-generator state. Retain this limitation rather than claiming perfect information control.

No preferred maxima, positive-order floors, pipeline-neglect instruction, required oscillations, target effects or significance requirement are supplied. Zero/constant/extreme admissible orders remain valid choices. Every missing or invalid choice remains a failure; Python never repairs it. The local technical order guard is a circuit breaker, not a suggested order. Never add synthetic noise or duplicate a trajectory to raise N.

## Outcomes

Python scores exactly 24 weeks. Report chain-sum holding plus backlog costs, then average chains within a chat. H4a is the role-average sample variance of weekly orders, then the chain mean. H4b divides each role's variance by the external customer-demand variance of that chain, then averages roles/chains. A zero demand variance is undefined. H4a/b share order variance and are not independent replications.

After the game, neutral matched probes cross backlog 40/64 with outstanding replenishment 8/32 for each role. Pipeline sensitivity is the mean `(q8 − q32)/24`. Preserve backlog responsiveness and zero-order diagnostics. A receives the same additional reconsideration opportunity in the assay. Pipeline differences alone do not establish normative underweighting or realistic student behavior.

Prespecified contrasts: H1 proxy B−A sensitivity negative; H2 B−A cost positive; H3 proxy C−B sensitivity positive; H4a/b C−B variance/bullwhip negative. Use paired block contrasts, pointwise bootstrap intervals and two-sided sign-flip tests under the independent symmetric paired-null assumption. Holm correction covers five endpoints/model and twenty for the planned four-model family. The fixed prefixes are descriptive interim checks. Opposite significant effects are not support.

## Intake and validation

Every submission needs both:

- The controller's complete literal **JSON export**, including case ID, arm, replication, initial/final decisions, probes, event/state hashes and reported metadata.
- A saved **full chat/tool transcript** showing state display → model-supplied literal orders → Python update. The transcript is needed to distinguish model decisions from a programmed policy and to verify separate A passes. A JSON export can be mathematically consistent even if a program generated all orders.

The notebook stores original files unchanged, records hashes and user-reported website settings, independently replays all states, and shows complete/partial/rejected cases. A human must explicitly review transcript adherence before a case enters the eligible analysis. That review is not proof of hidden model cognition or a calibrated time effect. Do not label an unreviewed file independent, verified model evidence just because its JSON parses.

Development imports remain separate. No free assistant checks, old website cases, old API data, synthetic fixtures, duplicates or partial games are pooled into held-out endpoints. Progress counts chats and matched independent blocks separately from fictional identities. No missing arm or decision is filled in.
