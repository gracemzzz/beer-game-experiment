# Literature-grounded redesign of the LLM Beer Game

Reviewed 11 October 2026. This is a design review, not new empirical results. The implemented specification is [ANYTIME_PROTOCOL_20261011.md](../../docs/ANYTIME_PROTOCOL_20261011.md). The four fictional student profiles are in [config/student_profiles](../../config/student_profiles/).

## What the literature changes in this implementation

The revised study uses a common classroom brief, four declared personality profiles, paired treatment assignment, role balancing, a known stationary demand distribution, retained delivery delays, separate pipeline components, and direct bullwhip/cost outcomes. It measures actual computation and distinguishes a missing answer from a valid current-state submission. It does not instruct any profile to neglect the pipeline, overorder, or create bullwhip. A null or opposite-direction effect remains a result.

## Four student profiles, rather than one universal student

The implemented library crosses working style (methodical/organized or flexible/informal) with emotional framing (steady or uncertainty-sensitive). These dimensions provide a small, inspectable set of fictional personalities. They are not copied survey respondents, psychometric measurements, diagnoses, or calibrated UB population frequencies. The profile descriptions deliberately omit ordering rules and the expected hypothesis direction. Each participant retains the same profile for the whole game.

Each chain contains one of each profile. The paired comparison uses the same profile-role mapping under both computation conditions. A randomized rotation balances profiles across roles over four pairs. This prevents a permanent identification of one personality with the factory or retailer. With only one pair, profile-specific results are descriptive and remain entangled with role. Broad personality interactions need a larger separately planned design.

The literature does not establish that requesting personality traits faithfully creates those traits in an LLM. [Bisbee et al. (2024)](https://doi.org/10.1017/pan.2024.5) found that persona-conditioned survey responses can differ from human variability and associations. We therefore call this a study of configured LLM participants. No human observations exist in the project, as confirmed by the user.

## Why change the computation treatment

The old single-call caps either truncated before an answer or were too generous to separate actual computation. The revision protocol first obtains a valid submission, then grants one condition additional computation. An exhausted revision retains that same-state submission, rather than fabricating an action. Both calls use the same pinned model and high effort. Total actual generation, including the initial phase, must separate on development and held-out states and is checked again in games.

This tests access to extra deliberation. It does not isolate a pure token-count effect from the opportunity to reconsider with a refreshed context. It also does not independently manipulate information quantity. Those are explicit boundaries of the claim, not problems solved by renaming the condition. [OpenAI's reasoning guide](https://developers.openai.com/api/docs/guides/reasoning) confirms that reaching a generation cap can prevent any visible answer.

## Cost options and temperature

| Option | Implementation/status | Tradeoff |
| --- | --- | --- |
| Share identical initial draws within a paired decision | Implemented; full prompt equality required | Up to one of three calls saved relative to independent initial submissions; analyze pairs, not independent chains within a pair. |
| Reuse exact checkpoints and compatible calibration | Implemented | Saves repeated purchases, but creates no new independent observations. |
| Stable prompt prefix / provider input caching | Used automatically; cached usage recorded | Saves eligible input cost, not reasoning output cost. No cache hit is assumed by the hard budget guard. |
| Offline simulator, known-policy checks and report generation | Implemented | Free software validation; never labeled human or API evidence. |
| Smaller prespecified feasibility game, then larger study | Notebook supports 24/32/40+ week plans | A shorter pilot is cheaper but gives noisier dynamic measurements; never shorten after seeing outcomes. |
| Batch API | A documented future option, not implemented in this runner | OpenAI documents 50% lower cost and up to a 24-hour turnaround. Games depend on preceding weekly choices, so many sequential batches can be slow. Independent state/probe batteries suit batching better. [Batch documentation](https://developers.openai.com/api/docs/guides/batch). |
| Switch to a cheaper model | Requires a separate protocol and calibration; not done silently | Model behavior changes. Cheap calls with an invalid treatment or poor rule comprehension are not economical evidence. |

Temperature remains omitted and identical in all conditions. Heterogeneity comes from declared profiles and repeated independent model draws, not a temperature change correlated with treatment. Deliberately raising temperature to manufacture interesting orders would not validate a student population. A future temperature robustness study must keep its setting constant across token conditions and record model/API support.

## What remains empirical

The software can now run a complete, auditable comparison without inventing decisions after revision truncation. It cannot promise a nonzero treatment effect, distinct behavior for every persona, identified dynamic beta, or human realism. The next live feasibility screen tests whether the actual computation contrast works. If it fails, the runner preserves a partial report and buys no games. A larger hypothesis study needs enough independent paired chains and a justified effect/variance-based power plan. The old pilot's evidence and its report are preserved separately.
